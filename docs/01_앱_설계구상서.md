## 0. Executive Summary (결론)

> **현재 운영 시스템(v4.1.1)은 기능이 완성되어 있으나 "구글 웹페이지"라서 앱처럼 쓰기 불편함 → 화면·데이터·로직은 100% 그대로 두고, '포장(앱 껍데기)'과 '통신선'만 바꾸는 PWA 방식으로 개강 전 앱화한다.**

| 구분 | 내용 |
|---|---|
| **핵심 전략 3가지** | ① **재사용 극대화** — 원본 화면 코드(Index.html)·서버 코드(Code.gs)·구글 시트 17개를 그대로 사용 ② **통신 계층만 교체** — `google.script.run` 6개 호출을 인터넷 API 호출로 바꾸는 "변환 어댑터" 1개 추가 ③ **설치형 앱(PWA)** — 홈 화면 아이콘·전체화면·구글 안내 띠 제거 |
| **비용** | 0원 (GitHub Pages 무료 호스팅 + 기존 Google 계정) |
| **일정** | 10/12 QA 앱 완성 → 10/14 UAT → 10/16 실운영(PROD) 전환 → 10/18 개강 |
| **안전장치** | 앱에 문제가 생기면 **원본 v4.1.1 웹앱 주소를 그대로 사용**(Plan B). 같은 시트를 쓰므로 데이터 손실 없음 |

### 1-4. 데이터·서버 구조

| 항목 | 내용 |
|---|---|
| 저장소 | 구글 스프레드시트 1개 × 시트 17개 (`v4_Config`, `v4_Access`, `v4_Trainee`, `v4_WeeklyCare` 등) |
| 로그인 | 이메일 → 6자리 인증코드(10분) → 14일 유지 토큰 |
| 보안 | 5회 오류 시 무효, 30분 5회 제한, 서버에서 역할 재검증(OPS 표), 버전 충돌 감지, Audit Log |
| 알림 | Red Care 즉시 메일 + 1시간 재확인, 매일 07시 할 일 요약 메일 |
| **화면↔서버 연결** | **단 6개 함수**: `bootstrap` `refresh` `requestLoginCode` `verifyLoginCode` `logout` `apply` |

> **Insight** — 화면과 서버의 접점이 6개뿐이라는 것이 이 프로젝트의 핵심 기회입니다. 접점만 바꾸면 1,352줄 화면 코드를 다시 짤 필요가 없습니다 → **"최대한 동일하게"를 가장 확실하게 달성하는 길**.

### 1-5. 원본의 앱 사용성 한계 (Pain Point)

| 문제 | 영향 |
|---|---|
| 상단에 "Google Apps Script 사용자가 만든 앱" 안내 띠 (숨길 수 없음) | 화면 공간 손실, 신뢰감 저하 |
| 홈 화면 추가 시 "바로가기"일 뿐, 브라우저 주소창이 남음 | 앱 느낌 부족 |
| 웹앱이 iframe 안에서 실행 | 아이폰에서 로그인 유지 불안정, 화면 잘림 |
| 앱 아이콘·시작 화면 없음 | 운영진이 매번 링크를 찾아야 함 |

## 2. 구현 방식 결정 (Decision)

### 2-1. 대안 비교 — Weighted Matrix

평가 기준: **원본 동일성 35% · 개강 전 완성 가능성 30% · 초보자 유지보수 20% · 비용 15%** (5점 만점)

| 대안 | 설명 | 동일성 35% | 일정 30% | 유지보수 20% | 비용 15% | **가중점수** |
|---|---|:-:|:-:|:-:|:-:|:-:|
| **A. PWA + 기존 서버 (추천)** | 원본 화면을 GitHub Pages에 올리고 통신만 교체 | 5 | 5 | 4 | 5 | **4.80** |
| B. 원본 웹앱 그대로 | 변경 없음, 홈 화면 바로가기 | 5 | 5 | 5 | 5 | 5.00 (단, Pain Point 미해결) |
| C. Flutter / React Native 앱 | 앱스토어용 네이티브 앱 새로 개발 | 2 | 1 | 1 | 2 | 1.50 |
| D. Firebase 등 새 서버 | 서버·DB 전부 재구축 | 2 | 1 | 2 | 3 | 1.85 |

> **결론** — B는 점수가 높지만 "앱을 만들어 달라"는 목적(Pain Point 해결)을 충족하지 못하므로 **Plan B(비상용)**로 유지하고, **A를 주력**으로 갑니다. C·D는 개강(9일 후) 전에 원본 수준의 검증을 끝낼 수 없습니다.

### 2-2. PWA란? (초보자 설명)

| 질문 | 답 |
|---|---|
| PWA가 뭔가요? | "설치할 수 있는 웹사이트"입니다. 인터넷 주소로 열고, **홈 화면에 추가**하면 아이콘·전체화면으로 일반 앱처럼 실행됩니다 |
| 앱스토어에 올려야 하나요? | 아니요. 링크만 단톡방에 공유하면 됩니다 (심사·수수료 없음) |
| 아이폰·안드로이드 모두 되나요? | 예. 아이폰은 Safari, 안드로이드는 Chrome에서 설치합니다 |
| 업데이트는요? | GitHub에 코드를 올리면 다음 실행 때 자동 반영됩니다 |

### 3-1. 바뀌는 것 vs 그대로인 것

| 구분 | 그대로 (원본 재사용) | 신규 추가 (최소) |

| 서버 | Code.gs 전 기능·권한·알림·Audit | `Api.gs` (doPost: 6개 함수만 통과시키는 관문) |

### 3-2. 통신 어댑터 설계 (핵심 기술 포인트)

| 항목 | 설계 |
|---|---|
| 방식 | 화면에 가짜 `google.script.run` 객체를 만들어, 내부에서 `fetch(POST)`로 Apps Script `/exec` 주소 호출 → 원본 화면 코드는 수정 없이 동작 |
| 요청 형식 | `{fn:"apply", args:[op, p]}` · Content-Type `text/plain` (브라우저 사전검사(CORS) 회피) |
| 허용 목록 | `bootstrap, refresh, requestLoginCode, verifyLoginCode, logout, apply` **6개만**. 관리 함수(setupV4·seedQASample 등)는 원천 차단 → **원본보다 보안 강화** |
| 오류 처리 | 서버 오류 메시지를 원본과 동일하게 FailureHandler로 전달 (CONFLICT·로그인 만료 처리 그대로) |
